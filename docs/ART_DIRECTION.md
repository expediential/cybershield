# Art Direction — CyberShield / Sentinel

## Intent

CyberShield should feel like a reliable piece of personal safety equipment: precise, dense where it needs to be, and quiet when there is nothing to act on. Sentinel rejects the previous editorial, light-card direction and also rejects an imitation hacker terminal.

## Composition

- Home is built around the **Sentinel Core**, not a stack of repeated cards. Its six perimeter nodes map to the six real security modules.
- Protection is a task index with numbered rails and full-width module rows, so the breadth of the product is immediately visible.
- Scan is a focused workbench. URL inspection uses a forensic breakdown; file assessment uses a file target and engine boundary.
- Network, Wi-Fi, and Bluetooth use dark technical fields, relationship lines, and stateful nodes. They never animate fictional activity in normal mode.
- Activity and alerts use chronology, source labels, and compact data rows rather than dashboard tiles.

## State language

| State | Visual treatment | Meaning |
| --- | --- | --- |
| Ready | Acid-lime rail/dot | The described local action can run now |
| Permission required | Amber rail/dot | Android access is needed before the action can exist |
| Setup required | Teal/neutral diagnostic state | A native or backend service has not been connected |
| Review | Amber finding and alert boundary | A local assessment found a signal needing judgment |
| Block | Coral threat boundary | A concrete high-risk local finding was recorded |
| Demo | Amber `DEMO` label | Isolated sample data, never real device data |

## Deliberate exclusions

- No green “device security score” based on arbitrary constants.
- No decorative hacker rain, terminal text, neon-on-black overload, or stock shield icons.
- No permanent motion for inactive monitoring.
- No demo detection can appear in local history, analytics, or a real alert.
